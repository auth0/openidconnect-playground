# Run work as an interactive, gated session driven by ENTRY_POINT.md

## Context and problem statement
The kit had the right documents (spec, plan, tasks, skills, commands) but no single script tying them into one working session. The human had to remember the order, retype the sequence of prompts, and decide when to move on. Separately, `CLAUDE.md` said "never commit or push" (from the kick-off recommendations), while the real flow needs a commit and push to trigger CI and another after the review fixes.

## Decision drivers
- One repeatable flow with the human in control at every step · reuse of the existing specs, skills and commands · the dev manager still approves · commits stay accountable to the human (constitution article XI) · little ceremony for small changes

## Considered options
1. Keep separate documents and rely on the human to prompt each step.
2. A single `ENTRY_POINT.md` that scripts ten phases with an explicit approval gate after each, a spec folder per change, and a commit gate. Smaller changes use shorter paths.
3. A CLI or framework that enforces the phases (for example Spec Kit).

## Decision outcome
Chosen: **Option 2**. The session starts with "Use ENTRY_POINT.md". The phases are requirement, plan, design, implementation, QA, CI, Copilot review, final commit and push, final check, close. The agent stops at every gate and proceeds only on the human's explicit approval. The spec folder gains `design.md` (the "how", after the plan) and `session.md` (checklist, follow-ups, evidence and the final summary).

**Commit and push.** The "never commit or push" rule becomes: never on its own. The agent may commit and push only at a commit gate: it stages the change by path, summarizes the staged diff, suggests a message, and acts only after the human approves. Commits are authored by the human: no agent author, no `Co-Authored-By` trailer, no "generated by" line. No force-push, amend, rebase, `--no-verify`, or push to the default branch. This is an explicit instruction in the sense of constitution article XI.

### Consequences
- Good: one flow end to end; the human decides at each step; evidence and a summary are written in the repo; the second-agent review, Copilot review and CI handling are part of the flow, not extra prompts.
- Bad / trade-offs: more steps than the kick-off recommendations assumed (small and trivial sizes get shorter paths to compensate); `ENTRY_POINT.md` must be kept in sync with the skills, commands and templates it names; the commit gate deviates from the original "leave changes uncommitted" rule and needs the dev manager's agreement.

### Confirmation
Run one real change through all ten phases and keep its `session.md`. Review `ENTRY_POINT.md` with the other context files quarterly. Track the metrics in ADR 0001 (rework rate, review rounds and time, CI failures from rules already in `CLAUDE.md`).

## Pros and cons of the options
1. Cheapest, but the order lives in the human's head and every session retypes it.
2. Slightly more documents to maintain; the human stays in control and nothing needs tooling beyond Markdown.
3. Stronger enforcement, but ties us to a product and a CLI; ADR 0001 already chose Markdown templates over frameworks.
